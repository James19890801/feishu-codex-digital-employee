本轮已完成代码级加固、自动化回归、依赖审计、真实服务重启、WebSocket 故障注入和一条历史漏回消息的端到端补偿验收。

- 回复不添加固定 AI 标签。
- 用户消息轮询为主，WebSocket 为辅助。
- SQLite 收件箱持久化、原子领取、幂等发送、重试和死信已启用。
- LaunchAgent 常驻并自动拉起。

- 生产依赖审计为 0 个已知漏洞。
- 飞书待办、日程和 Multica 写入已加入持久化执行账本，崩溃恢复不会盲目重复外部写操作。

## 已发现并修复的问题

1. 进程崩溃后，刚进入 `processing` 的消息可能永久卡住。现改为启动时立即恢复全部处理中租约。
2. 只有 @、没有附带文字的群消息会被静默吞掉。现增加裸 @ 快速回复路径，不再调用模型。
3. 子进程没有统一超时、输出上限和退出升级策略。现增加 SIGTERM、宽限期、SIGKILL、stdout/stderr 上限。
4. 子进程提前退出时，stdin 写入会触发未处理的 `EPIPE` 并打崩服务。现已捕获并回归测试。
5. 无输入的 CLI 仍使用 pipe 型 stdin，导致 Codex 等待额外输入、飞书搜索输出完成却不退出。现无输入时使用 `/dev/null`。
6. Persona、Bible 和聊天内容曾暴露在进程命令行参数中。现全部通过 stdin 传递，`ps` 不再显示内容。
7. Codex 子进程未继承本机代理，直连 OpenAI 超时。现显式配置可信本机代理，并加入真实采样测试。
8. Codex 会加载主账号的无关技能和配置。现使用隔离 Codex Home，只链接登录凭据。
9. 会话串行队列清理条件错误，Map 长期不释放。现改为可测试的 `SerialKeyQueue`。
10. SQLite 中单条损坏 JSON 会阻断整个收件箱。现损坏记录会被隔离并标记完成。
11. 服务关闭时退避等待不可中断，且 Codex/Python/飞书 CLI 子进程可能成为孤儿。现统一登记和终止。
12. SDK WebSocket 的 `start()` 会立即返回，旧实现可能形成连接风暴。现持续检查连接状态并显式关闭。
13. 限流后每条消息仍发送提示，可能被利用放大外发。现每个窗口最多发送一次限流提示。
14. 会话、审计、已完成消息、限流记录、过期确认和日志可能无限增长。现加入周期清理、WAL checkpoint 和日志轮转。
15. 手工误启动第二个实例会恢复第一个实例正在处理的消息。现加入带 PID/令牌校验的单实例锁。
16. 最终错误提示发送失败时可能无限重试原任务。现进入死信，避免重复执行高成本操作。
17. `event status --fail-on-orphan` 对“总线运行但无消费者”可能假阳性。现强制校验 `active_consumers >= 1`。
18. 未使用的 `@larksuiteoapi/lark-mcp` 引入 1 个中危漏洞和 137 个多余包。现已移除，生产依赖由 189 降至 52，漏洞为 0。
19. 服务安装时 `bootout` 后立即 `bootstrap` 偶发 macOS I/O error。现增加最多 10 次有界重试。
20. SDK 业务客户端缺失时，文档、媒体、待办、日程可能给出误导性错误。现明确回复“能力未配置”，不伪装成功。
21. 任意联系人可触发账号侧写操作。现只有账号本人可以创建待办、日程或批量行动项。
22. Python 文件处理依赖只存在于开发机，仓库无法证明换机后可复现。现增加锁定版本的 `requirements.txt`、安装步骤和运行时导入检查。
23. README 曾把 Node.js 要求写成 20+，与 `node:sqlite` 的实际运行门槛不一致。现将引擎要求和文档统一为 Node.js 22.5+。
24. 主轮询收到“总结刚才的文件”时缺少最近文件回查，文件能力可能只在特定事件入口生效。现按同一会话、同一发送者和 30 分钟窗口回查，且有独立回归测试。
25. 飞书限流后首次重试仅等待 2 秒，比正常 5 秒轮询更激进，可能形成持续限流。现识别错误消息及 CLI `stderr` 中的 429/`too many request`，进入至少 60 秒并带抖动的冷却；普通错误也不会比正常轮询更快重试。该 `stderr` 包装场景已在真实群消息回归中复现并加入自动化测试。
26. 外部写操作成功、但本地来不及记录结果时，重启后可能重复创建待办、日程或 Multica Issue。现先持久化执行意图，再执行外部写入；已成功结果直接回放，结果不确定时停止自动重放并要求人工核对。
27. Multica 通知失败会永久指数重试。现最多尝试 10 次，随后进入死信；死信数量同时进入面板、状态回复、健康检查和审计。
28. SQLite `synchronous=NORMAL` 无法提供本机可实现的最高提交耐久性，也没有可验证恢复点。现提升为 `FULL`，并在启动和每 6 小时维护时执行在线备份、只读 `quick_check` 和 14 份滚动保留。
29. 面板只检查 AI CLI 是否存在和代理端口，真实调用已经失败时仍可能显示绿色。现记录最近一次真实 AI 成功/失败；最新结果为失败时，AI 卡片和总状态都会降级。
30. 数据库卡片曾只看主库完整性，备份过期时卡片仍可能显示绿色。现数据库卡片同时要求主库完整、备份新鲜且最近备份无错误。

## 仍然存在的边界

### R1：单机不是多节点高可用

Mac 关机、休眠、用户退出、磁盘损坏或整机断网时，服务无法在线响应。LaunchAgent 只能处理进程级故障。若要求 99.9% 以上服务可用性，需要常开主机、第二节点、共享持久化和主节点选举。

### R2：飞书搜索接口没有端到端 SLA

轮询依赖用户消息搜索接口的时效和完整性。程序已在分页不完整时拒绝推进游标，并用 3 分钟重叠去重，但飞书上游故障仍可能带来延迟。超过 24 小时离线的消息按当前配置不会补追。

### R3：图片、文件、文档、待办和日程依赖额外 SDK 业务凭据

核心文字问答和真人身份回写只依赖用户 OAuth。媒体、文档、待办和日程还依赖专用 Keychain 中的 App Secret、对应飞书应用权限以及实际资源可见性；任一条件缺失时，SDK 业务客户端会降级并明确提示不可用。换机或变更应用权限后必须重新做对应能力的真实验收。

### R4：Codex 仍依赖本机代理和 OpenAI 可用性

本机直连 OpenAI 会超时，当前通过可信代理 `127.0.0.1:7897` 工作。代理退出或上游波动会触发超时和重试。健康检查会检测代理端口，真实采样检查可用 `npm run codex-smoke`。

### R5：只读沙箱不等于零信任隔离

Codex 已在隔离目录、隔离 Home 和只读沙箱运行，提示词也禁止读取本机文件。但只读沙箱理论上仍可能读取操作系统允许访问的文件。严格零信任需要独立 macOS 账号/虚拟机/容器，或改用不提供本机工具的模型 API。

### R6：真人身份自动回复的治理风险

取消白名单和 AI 标签是明确配置，但意味着所有联系人都能触发低风险自动回复。代码已限制账号写操作、敏感动作和速率；仍建议在组织治理层面明确授权范围、告知方式和人工接管责任。

### R7：端到端延迟不是固定值

裸 @ 走快速路径，主要耗时为轮询和飞书发送。带问题的消息还包含模型生成，最近最小采样约 9 秒；网络拥塞或复杂任务可能接近 120 秒硬超时。不能承诺所有问题都在固定秒数内完成。

### R8：备份仍位于同一台 Mac

滚动备份可以恢复误操作、应用故障和主数据库损坏，但无法覆盖整机丢失或系统盘物理损坏。正式商业部署还应配置加密的异机或对象存储备份、保留策略和定期恢复演练。

### R9：结果不确定的外部写需要人工核对

飞书和 Multica 当前没有统一的幂等键查询协议。网络在提交后断开时，系统会选择“停止重放并提示核对”，从而避免重复创建。若要完全自动对账，需要目标系统支持幂等键，或增加按业务字段查询和人工确认的对账工作台。

### R10：商业运维仍需要值班和远程告警

当前面板、飞书状态回复、审计和本机健康检查能够暴露故障，但尚未接入独立的远程监控、电话/短信升级、值班轮换和服务等级报表。需要 7×24 商业承诺时，应把这些能力作为部署环境的一部分。
