# 微信单聊红包自动领取设计

日期：2026-09-03

## 目标

当当前个人微信账号收到一对一单聊中的普通微信红包时，自动在本机微信客户端完成领取。群聊红包、转账、收款、自己发送的消息，以及任何无法可靠确认会话类型或目标会话的事件，一律不执行。

## 已确认边界

- 默认开启范围仅为个人微信单聊红包。
- 不提供发送红包能力。
- 群聊红包必须在事件入口和执行入口分别拒绝。
- 转账、收款、小程序红包、营销红包链接等非普通聊天红包不处理。
- 不自动发送感谢语或其他消息。
- 领取失败不得反复点击；结果要可审计，但不得记录红包金额、密钥或完整消息 XML。

## 技术选择

采用“GeWe 事件识别 + 本机微信受控 UI 执行”的混合方案。

GeWe v2 Webhook 能明确提供 `RED_PACKET` 事件和单聊/群聊原始会话标识，但当前公开 API 目录没有领取红包接口。本机微信 4.x 支持领取单聊红包，因此复用仓库中已有的 macOS 窗口识别、OCR 和受保护点击能力完成最后两次交互。

不采用纯 GeWe 方案，因为没有可依赖的公开领取接口；不采用纯轮询屏幕方案，因为仅凭视觉难以可靠区分消息来源、去重和审计。

## 数据流

1. GeWe Webhook 收到消息后，规范化层只把明确的红包消息转换为 `message_type=red_packet`。
2. 规范化结果必须同时满足：`chat_type=p2p`、非本人消息、发送者和消息 ID 完整、目标不是 `@chatroom`。
3. 红包事件不进入 AI 回复链路，而是进入独立的红包领取协调器。
4. 协调器按消息 ID 做持久化幂等，并通过 GeWe 联系人信息解析目标会话显示名。
5. macOS 执行器打开并验证目标会话，确认界面是单聊，定位未领取的普通红包卡片。
6. 执行器点击红包卡片；只有出现受支持的领取弹窗和明确的“开”控件时才继续点击。
7. 执行后通过界面状态验证“已领取/已被领完/已过期”等结果，写入最小审计状态。

## 双重安全门

### 事件门

- `chat_type` 必须严格等于 `p2p`。
- `fromUser`、`toUser`、目标 ID 中任何一个表现为 `@chatroom` 都拒绝。
- 仅接受普通 `RED_PACKET`，不把 `TRANSFER` 或通用 `APP_MSG` 猜测为红包。
- 配置开关未开启时只识别、不执行。

### UI 门

- 必须取得新鲜的目标会话证明，过期后重新验证。
- 会话标题、窗口、会话种类必须与目标证明一致；出现群成员计数、群标志或无法判定时拒绝。
- 必须定位到聊天区内的未领取红包卡片，不能按固定屏幕坐标点击。
- 第二次点击只允许作用于领取弹窗中的“开”控件。
- 任一步骤不确定都失败关闭，不尝试猜测或继续点击。

## 状态、重试与审计

每个红包事件以 `appId + newMsgId` 为幂等键，状态为：`detected`、`claiming`、`claimed`、`not_claimable`、`failed`、`skipped_group`、`skipped_disabled`。

- `claimed`、`not_claimable` 和所有 `skipped_*` 状态不再重试。
- 只有客户端暂时不可用、锁屏或 UI 尚未同步时允许有限重试。
- 重试使用短退避并设置最大尝试次数与事件有效期，避免红包过期后持续操作。
- 审计只保存消息 ID 哈希、发送者 ID 哈希、会话类型、时间、状态、失败原因和尝试次数。

## 配置与运行约束

新增独立配置开关，默认关闭；启用后仍要求 GeWe 在线、本机微信 4.x 已登录、屏幕解锁、辅助功能与录屏权限齐全。

建议配置：

- `geweDirectRedPacketAutoClaimEnabled=false`
- `geweDirectRedPacketClaimMaxAttempts=3`
- `geweDirectRedPacketClaimTtlMs=3600000`

## 测试与验收

确定性测试覆盖：

- v1/v2 单聊红包正确规范化。
- 群聊红包无论是否 @ 当前账号都被拒绝，且执行器调用次数为零。
- 转账、收款、普通应用消息不触发。
- 重复 Webhook 只执行一次。
- 锁屏、客户端离线、会话类型不确定、找不到红包卡片或找不到“开”按钮时安全退出。
- 已领取、已过期、已被领完不重试。
- 配置默认关闭，开启需要受保护配置变更。

实机验收使用测试联系人发送小额单聊红包，确认自动领取、手机钱包同步和审计状态；再在测试群发送红包，确认零点击、零领取。

## 风险

个人微信自动化及第三方 GeWe 均可能触发账号风控。该能力不绕过支付验证，不读取或保存支付密码，但仍属于账号自动化操作。上线前必须先在测试账号或可接受风险的账号上小额灰度，并保留一键关闭能力。
