# 微信单聊红包自动领取可行性结论

日期：2026-09-03

状态：暂不实施，等待服务商提供公开、稳定的领取接口。

## 目标边界

仅允许通过当前个人微信服务端接口自动领取一对一单聊中的普通微信红包。

- 不登录或控制本机 Mac 微信客户端。
- 不使用 OCR、屏幕识别、辅助功能、坐标点击或其他 UI 自动化。
- 不发送红包。
- 不领取群聊红包。
- 不把转账、收款、小程序红包或营销红包链接视为普通红包。

## 核实结果

当前 GeWe v2 Webhook 文档定义了 `RED_PACKET` 回调，因此系统可以识别“收到红包”事件，并可根据 `fromUser`、`toUser` 与 `@chatroom` 后缀判断单聊或群聊。

但是，当前 GeWe 公开 API 目录没有领取、打开或接受红包的接口。消息模块公开的执行能力包括发送消息、下载、转发和撤回等，不包括红包领取。`RED_PACKET` 是入站通知类型，不是可执行的领取动作。

仓库当前的 `GeWeChannel` 也没有红包领取方法。仅根据非公开协议猜测接口路径、拼装底层红包参数或直接调用微信私有协议，不满足“通过已有接口实现”的要求，也会带来账号和资金操作风险。

## 决策

本期不实现自动领取，也不只实现“检测到红包”这种无法完成业务闭环的半成品。

若 GeWe 后续提供公开领取接口，必须至少明确：

1. 稳定的接口路径、鉴权方式和版本承诺。
2. 从 `RED_PACKET` 回调中取得的必要字段及其含义。
3. 单聊与群聊参数的确定性区别。
4. 重复调用的幂等语义。
5. 已领取、已过期、已被退回和风控失败的错误码。
6. 该能力是否属于服务商正式支持范围。

满足以上条件后，按“事件门 + API 门”实现：只接受 `chat_type=p2p` 且所有原始会话标识均不含 `@chatroom` 的事件；在调用前再次拒绝群聊目标；使用 `appId + newMsgId` 持久化幂等；不记录金额、完整 XML 或支付敏感字段。

## 验收红线

- 群聊红包的领取 API 调用次数必须为零。
- 转账、收款和通用应用消息的领取 API 调用次数必须为零。
- 重复 Webhook 最多触发一次成功领取。
- 接口文档、字段或会话类型不完整时失败关闭。
- 不引入任何本机微信客户端依赖。
