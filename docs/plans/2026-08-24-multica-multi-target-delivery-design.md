# Multica 多目标渠道交付设计

## 背景

BEIJ-4 已生成 PDF、HTML 两份附件。用户在微信私聊明确要求把交付物发送到「AI流程与组织变革交流一群」和「AI流程与组织变革交流二群」，但人工恢复创建时只记录了私聊来源，没有建立群交付契约。现有 `multica_delivery_contract` 又以 `issue_id` 为主键，一条 Issue 只能描述一个目标会话。

Multica 小队运行环境只负责处理 Issue 和生成附件，不直接持有微信发送能力。微信发送应由 AIPRO 的渠道交付层执行。

## 方案比较

1. 将现有交付契约表改成 `(issue_id, channel, chat_id)` 复合主键。模型直接，但需要重建线上表并改写所有单契约调用，迁移风险较高。
2. 保留现有父契约，新增独立的多目标子表。父契约描述所需格式和整体状态；每个目标独立记录附件投递、尝试次数和错误。采用此方案。
3. 在父契约中新增目标 JSON。改动较少，但难以原子认领单个“目标+附件”，部分成功后容易重复发送。

## 数据模型

新增 `multica_delivery_target`：

- `issue_id`
- `channel`
- `chat_id`
- `sender_id`
- `chat_type`
- `status`
- `artifact_ids`
- `attempts`
- `last_error`
- `created_at`
- `updated_at`
- `delivered_at`

主键为 `(issue_id, channel, chat_id)`。启动迁移会为每条旧父契约补建一个目标行，并复制原来的投递状态和附件记录，保持历史幂等性。

## 投递流程

1. 父契约继续保存 Issue、空间、格式和原始要求。
2. 新建或补充交付契约时可传入 `targets`；旧调用仍可传单个 `channel/chatId`。
3. 同步器只下载一次符合格式的附件。
4. 对每个目标和附件执行原子认领，幂等键包含附件 ID 与目标会话。
5. 成功目标记录已发送附件；失败或结果不确定只冻结对应目标，不影响已经完成的目标。
6. 所有目标都收到所有要求格式后，父契约才标记为 `delivered`。
7. 审计记录每个目标的成功、失败和最终汇总。

## BEIJ-4 补发

为 BEIJ-4 建立格式为 `pdf/html` 的父契约，并加入两个微信目标：

- `wechat:group:54103319902@chatroom`：AI流程与组织变革交流一群
- `wechat:group:53822548488@chatroom`：AI流程与组织变革交流二群

通过正式 `MulticaArtifactDelivery` 链路触发同步，而不是绕过系统直接调用微信。预期共四次文件发送（2 个文件 × 2 个群），每次均有独立幂等记录；随后核验父契约、两个目标、微信服务商回执和审计记录。

## 错误处理

- 目标群不存在或渠道离线：该目标记为失败/不确定，其他目标保持成功状态。
- 发送调用已发出但结果不确定：该目标进入 `delivery_ambiguous`，自动重试停止，避免重复。
- 没有匹配附件：父契约保持 `waiting_artifact`，不调用渠道。
- Multica 执行者不得再声称“系统未接入微信”；它只需上传附件，渠道能力由 AIPRO 判断和执行。

## 测试与验收

- 状态测试：旧契约迁移、多目标增补、目标级原子认领、部分成功不重复。
- 投递测试：两个附件发送到两个目标，共四次；第二次同步为零次。
- 故障测试：第二个目标失败不会重发第一个目标。
- 全量测试和机制验收通过。
- 生产验收：两个群均收到 PDF、HTML；父契约与两个子目标均为 `delivered`；微信和 Multica 健康检查通过。
