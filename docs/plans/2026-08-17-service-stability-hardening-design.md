# AIPRO 服务稳定性加固设计

## 背景与根因

2026-08-17 的掉线不是微信账号失效，而是主服务的 LaunchAgent 被一次临时安装审计覆盖。内存中加载的服务定义指向临时工作目录，正式主进程收到 SIGTERM 后，`KeepAlive`、Dashboard 重启、macOS App 重启和隧道监督器都只会对同一个错误定义执行 `kickstart`。临时目录缺少 `config.local.json`，因此错误定义持续退出；陈旧的 `data/service.lock` 又阻止正式安装脚本重新接管。

这是典型的共因失效：多个恢复入口共享同一个未经校验的 launchd 控制面，所以增加重试次数不会提高可用性。

## 目标

- 测试和安装审计绝不能操作真实生产 LaunchAgent。
- 重启前验证已加载定义是否属于当前正式安装目录。
- 服务定义漂移、服务缺失或陈旧锁出现时，自动恢复正式定义。
- shutdown 卡住时在有限时间内退出，让 launchd 能重新拉起。
- 每次恢复必须验证进程、监听端口和健康状态，失败时有限退避，避免重启风暴。
- 所有新行为可在不触碰真实 launchd 的单元测试中故障注入。

## 方案选择

采用“分层自愈”，不新增第二套常驻守护进程。

### 1. 测试与生产控制面隔离

`scripts/install-service.sh` 和 Dashboard 服务安装脚本通过显式变量选择 launchctl。生产默认使用 `/bin/launchctl`；测试必须注入 stub。测试环境若请求真实 launchctl，脚本直接拒绝。安装器测试继续使用临时 HOME 和临时安装根，但所有 launchd 操作只写入 stub 日志。

### 2. 可验证的服务定义协调器

新增纯逻辑模块负责：

- 解析 `launchctl print` 输出中的 plist 路径、程序、工作目录和 PID；
- 与正式 plist、正式工作目录和入口文件做严格比对；
- 输出 `healthy`、`missing` 或 `drifted` 判定以及恢复动作；
- 校验锁文件 PID 是否存在，且对应进程命令是否属于正式入口。

Dashboard 的重启不再无条件 `kickstart`：定义健康时才 kickstart；缺失或漂移时执行 `bootout` 后从正式 plist `bootstrap`。陈旧锁先改名留档，再恢复服务。

### 3. 有界恢复与健康闭环

恢复动作完成后轮询本地状态端点，要求：

- 主进程存活；
- 微信回调端口处于监听状态；
- 已启用的微信通道完成 callback registration 并连接。

重试采用有限次数和退避；同一故障持续失败时记录聚合错误并停止重启风暴。隧道监督器调用同一协调器，不再维护另一套仅 kickstart 的恢复逻辑。

### 4. 主进程退出兜底

shutdown 增加总超时。正常清理完成时取消计时器；超过上限则记录结构化错误并以非零状态强制退出，交由已校验的 LaunchAgent 重新拉起。

## 评审建议取舍

本次采纳：

- P0-2 中的配置解析错误增强，只改善错误定位，不擅自修改尚未确认的产品默认值；
- P0-6 主进程 shutdown 总超时；
- P1-4 CI 的冻结依赖安装、语法检查和测试；
- P1-6 CI 高危依赖漏洞扫描；
- P2-3 的稳定性专项集成测试，但不做广泛 E2E 重构。

本次不采纳：

- P0-1 schema 大规模迁移：与本次事故无直接因果，改动面过大；
- P0-3 自聊哈希：当前主链已经使用 `outbound_echo` 内容哈希；
- P0-4 时区集中化、P0-5 通知节流：有价值但不属于本次共因掉线；
- P1-1/P1-2 全链路日志改造、P1-5 核心模块全面 JSDoc、P1-7 文档门面：另行排期；
- P1-3 新增健康端点：已有机器可读 `/api/status`；
- P2 大拆 `index.mjs` 或 TypeScript 全量迁移：风险和本次目标不匹配。

## 测试策略

严格按 TDD 逐项增加：

1. 安装器测试证明注入的 launchctl 被使用，真实 launchctl 不可达。
2. 协调器测试覆盖健康定义、临时目录漂移、服务缺失和陈旧锁。
3. Dashboard 重启测试覆盖 `kickstart` 与 `bootout + bootstrap` 两条分支。
4. shutdown 测试覆盖正常退出和超时强制退出。
5. 故障注入 smoke 模拟错误 plist 与陈旧锁，验证恢复到正式入口。
6. 完成后运行 `npm run check`、专项测试、全量 `npm test` 和真实服务一次受控重启验证。

## 回滚

代码改动按独立提交拆分。若线上恢复验证失败，可回退协调器调用并重新加载当前正式 plist；不会修改业务数据、微信凭据或消息队列。
