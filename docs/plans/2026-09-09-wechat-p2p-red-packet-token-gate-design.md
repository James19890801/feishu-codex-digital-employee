# 微信单聊十次回复后红包解锁设计

日期：2026-09-09

状态：已确认

适用范围：个人微信 GeWe 通道的一对一单聊

## 目标

数字人对同一微信联系人累计成功回复 10 次后，在下一次回复机会请求对方发送小红包。未收到红包时，系统再发送一次结束提示，之后对该联系人的普通消息保持静默且不调用 AI。检测到真实的单聊红包卡片后，永久恢复正常回复。

回复次数按现有全部历史累计，永久不按天清零。上线前已有的成功回复和真实红包卡片都要从生产数据库回填。

## 已确认业务规则

1. 仅处理微信一对一单聊；群聊不受影响。
2. 前 10 次正常回复。只有发送接口确认成功的正常业务回复才计数。
3. 已累计 10 次且没有红包记录时，下一条普通入站不调用 AI，只发送一次：

   > 老板，我这边没 token 了，能不能发个小红包，给我续点 token 花一花？

4. 请求红包后收到的下一条非红包消息不调用 AI，只发送一次：

   > 红包都不发一个，不想跟你聊了，太浪费 token 了。

5. 此后的非红包消息全部静默。系统完成入站队列项并写审计，不发送消息，不调用 AI。
6. 任意阶段收到真实单聊红包卡片，都将该联系人永久解锁。系统可回复：

   > 红包收到啦，token 续上了，继续聊 😄

7. 历史上已经发送过真实单聊红包卡片的人，上线时直接标记为已解锁。
8. 老板账号、数字人自身消息、公众号或服务号、系统账号、群聊消息全部豁免。
9. 包含“红包”文字、红包退款通知、转账、收款、小程序营销链接和群红包不能解锁。
10. 本期只识别红包卡片作为游戏规则凭证，不自动领取红包，也不声称资金已经到账。

## 当前数据基线

当前生产数据库可识别 141 个微信单聊对象，其中 91 个有成功回复记录。历史累计成功回复达到 10 次的对象有 29 个：排除 1 个老板账号和 4 个公众号或服务号后，2 位联系人已有真实单聊红包卡片，剩余 22 位联系人将在下一条普通单聊消息时进入红包门槛。

完整盘点保存在 `outputs/wechat-p2p-relationship-reply-counts-2026-09-09.md`。统计只覆盖当前生产数据库，不代表微信平台的全量历史。

## 方案选择

### 方案一：每次动态扫描历史

每条入站都联查 `audit`、`inbound_message` 和人物关系数据，现场计算回复数与红包状态。改动少，但查询成本随历史增长，跨表口径容易漂移，也难以保证重试时只计一次。

### 方案二：把全部门槛状态放进人物主表

直接给 `relationship_person` 增加回复数、提醒状态和锁定时间。读取简单，但人物身份信息与微信运营策略耦合，后续变更阈值或策略时维护困难。

### 方案三：人物红包字段加独立门槛账本

在人物关系中保留用户要求的“是否发过红包”，另设微信单聊门槛表和成功回复账本。人物画像可以直接展示红包状态，运行时状态、幂等和迁移又有独立边界。

采用方案三。

## 数据模型

### 人物关系字段

给 `relationship_person` 增加：

- `has_sent_red_packet INTEGER NOT NULL DEFAULT 0`
- `red_packet_first_seen_at TEXT NOT NULL DEFAULT ''`
- `red_packet_source_message_id TEXT NOT NULL DEFAULT ''`

`has_sent_red_packet` 表示系统在单聊入站中检测到合格红包卡片，不表示红包已经领取或资金到账。证据消息 ID 用于追踪和幂等，不保存红包金额、完整 URL、签名或支付参数。

### 门槛状态表

新增 `wechat_p2p_token_gate`：

- `person_id TEXT PRIMARY KEY`
- `state TEXT NOT NULL`：`active`、`payment_requested`、`blocked`
- `reply_count INTEGER NOT NULL DEFAULT 0`
- `threshold INTEGER NOT NULL DEFAULT 10`
- `payment_request_source_message_id TEXT NOT NULL DEFAULT ''`
- `payment_requested_at TEXT NOT NULL DEFAULT ''`
- `blocked_source_message_id TEXT NOT NULL DEFAULT ''`
- `blocked_at TEXT NOT NULL DEFAULT ''`
- `updated_at TEXT NOT NULL`

人物关系的 `has_sent_red_packet=1` 优先于门槛状态。已发红包的人永久放行，不再重新进入门槛。

### 成功回复账本

新增 `wechat_p2p_reply_ledger`：

- `message_id TEXT PRIMARY KEY`
- `person_id TEXT NOT NULL`
- `sent_at TEXT NOT NULL`
- `created_at TEXT NOT NULL`

正常回复发送成功后，在一个数据库事务中 `INSERT OR IGNORE` 回复消息对应的入站消息 ID；只有首次插入才增加 `reply_count`。红包请求、结束提示、红包确认、老板审批消息和其他系统通知不计入免费回复次数。

## 红包识别

当前生产数据中的普通单聊红包为微信应用消息，结构特征包括：

- 应用消息类型为 `2001`；
- 标题或描述符合普通微信红包；
- URL 属于微信支付个人红包接收路径；
- 路径与参数同时包含个人红包必要标志；
- `chat_type=p2p`；
- 发送人不是数字人自身；
- 消息 ID 和发送人均存在。

规范化层应把合格事件转成 `message_type=red_packet`，并只保留经过裁剪的元数据，例如 `kind=personal` 和红包证据摘要。完整红包 URL、签名、发送编号及支付字段不得进入审计、人物关系或提示词。

红包检测采用结构化解析，不用关键词单独判定。无法完整解析、类型不匹配或来源不明确时失败关闭，不更新红包状态。

## 处理顺序

微信入站按现有聊天 ID 串行队列处理，门槛策略位于 AI 调用、人物记忆召回、网页读取和高成本审批之前：

1. 验证并规范化 GeWe 回调。
2. 保存入站并按消息 ID 去重。
3. 识别豁免对象。
4. 若为合格红包，幂等标记人物已发红包并放行。
5. 若人物已发红包，进入原有回复流程。
6. 若 `reply_count < 10`，进入原有回复流程。
7. 若已达到 10 次且状态为 `active`，发送红包请求，成功后改为 `payment_requested`。
8. 若状态为 `payment_requested` 且本条不是红包，发送结束提示，成功后改为 `blocked`。
9. 若状态为 `blocked` 且本条不是红包，直接静默完成。
10. 原有正常回复发送成功后，幂等记录回复账本并更新计数。

门槛提示发送失败时不能提前改变状态；入站保持可重试。使用由入站消息 ID 派生的稳定发送幂等键，避免进程中断后重复提示。

## 启动回填

启动迁移分两部分执行，并写版本标记以保证只运行一次：

1. 从 `audit.event='message_replied'` 联结微信单聊 `inbound_message`，按唯一入站消息 ID 生成回复账本和累计次数。排除自身活动、群聊、服务账号与系统账号。
2. 扫描已落盘的微信单聊应用消息，用同一结构化红包识别器回填人物红包字段。只记录最早合格消息的时间与消息 ID。

回填不得主动给任何联系人发消息。达到门槛的人只在下一条自然入站时收到红包请求。

## 豁免与身份

老板账号从 `geweOwnerWxids` 的有效配置读取；数字人自身使用回调中的当前微信 ID 与 `ownerActivity` 判断；公众号和服务号按稳定账号类型识别；系统消息继续使用现有系统身份。不得以显示名判断豁免，防止改名造成误判。

## 审计与可观测性

新增审计事件：

- `wechat_p2p_gate_reply_counted`
- `wechat_p2p_gate_payment_requested`
- `wechat_p2p_gate_blocked`
- `wechat_p2p_gate_suppressed`
- `wechat_p2p_gate_red_packet_detected`
- `wechat_p2p_gate_red_packet_backfilled`
- `wechat_p2p_gate_unlocked`
- `wechat_p2p_gate_backfill_completed`

审计记录人物哈希、来源消息 ID、状态变化和累计次数，不记录完整红包载荷。Dashboard 和人物列表展示累计回复数、当前门槛状态、是否见过红包卡片及最后状态更新时间。

## 错误处理

- 红包解析异常：不解锁，写裁剪后的解析失败审计，按普通非红包消息处理。
- 数据库写入失败：抛出错误，由入站队列重试；不能发送回复后丢失计数。
- 门槛提示发送失败：状态不前移，使用相同幂等键重试。
- 重复回调：入站消息 ID、红包证据消息 ID 和回复账本三层去重。
- 重启恢复：状态全部来自 SQLite，不依赖内存计数。
- 历史数据不完整：报告基线限制，不把无法查到的历史当作零；后续新消息仍按已确认累计数运行。

## 验证

至少覆盖以下行为：

1. 第 1 至第 10 次正常回复并准确计数。
2. 第 11 次请求只发送红包提示且不调用 AI。
3. 下一条非红包只发送一次结束提示。
4. `blocked` 后任意数量普通消息均静默且不调用 AI。
5. 合格单聊红包在 `active`、`payment_requested` 和 `blocked` 三种状态下都能永久解锁。
6. 群红包、红包文字、转账、退款、营销链接、结构不完整消息均不能解锁。
7. 老板、自身、公众号、服务号和系统消息不进入门槛。
8. 重复 Webhook、处理重试和进程重启不会重复计数、重复提醒或重复解锁。
9. 回填结果与生产盘点一致：29 个达到门槛，1 个老板豁免，4 个服务账号豁免，2 个联系人已有红包卡片，22 个联系人等待下一条消息触发门槛。
10. 日志、审计和人物数据不包含红包完整 URL、签名、发送编号或其他支付敏感字段。

## 上线方式

增加默认关闭的配置开关 `wechatP2pRedPacketGateEnabled` 和阈值 `wechatP2pRedPacketGateThreshold=10`。完成迁移和回填校验后启用生产配置，重启主服务，核对通道健康、回填汇总和门槛状态。上线过程不发送测试红包或主动触达联系人；使用构造回调完成本地验证，生产环境等待自然入站触发。
