# 跨渠道回复反向 @ 铁律设计

## 目标

所有群聊渠道统一执行一条不可降级的规则：只要数字人正在处理某位群成员发来的消息，回复就必须真实 @ 回该成员。个人微信必须使用 GeWe 的 `ats` 参数产生微信原生提醒，不能只在正文前拼接名字。

## 约束

- 单聊不添加 @。
- 主动群通知、新人欢迎等没有“当前发起人”的消息不添加 @。
- 群消息回复上下文必须携带当前发起人的稳定用户 ID。
- 需要 @ 但无法形成渠道原生 @ 时，发送失败并进入既有重试链路，禁止静默发送普通回复。
- 保留现有重复发送防护；@ 对象继续进入 audience key，避免不同收件人的回复互相误判为重复。

## 方案比较

### 方案 A：只拼接 `@昵称`

实现最简单，但个人微信不会产生真实提醒，无法满足铁律。

### 方案 B：只传渠道用户 ID

可以触发部分渠道的原生提醒，但个人微信 GeWe 同时要求正文包含 `@昵称`，展示和协议不完整。

### 方案 C：渠道原生 @ + 可验证发送契约（采用）

- 飞书：继续使用 `<at user_id="...">...</at>`。
- 钉钉：继续同时发送 `<@id>` 占位符和 `atOpenDingTalkIds`。
- 企业微信：群 Markdown 使用 `<@userid>`。
- 个人微信：从群成员列表解析昵称，正文加入 `@昵称`，请求体同时传 `ats=wxid`。
- 回复上下文标记 `mentionRequired`；发送层校验目标、用户 ID 和原生 @ 参数，缺任何一项都抛错。

## 数据流

1. 入站标准化得到 `chat_id`、`chat_type` 和发起人 ID。
2. `createReplyContext` 在群聊中保存发起人 ID，并标记 `mentionRequired=true`。
3. 所有 `sendText` 调用从异步上下文取得发起人 ID。
4. `prepareGroupMention` 生成飞书、钉钉、企业微信的原生标记；个人微信交给 GeWe 运行时准备。
5. GeWe 运行时校验群 ID 和 wxid，从群成员列表解析显示名，构造 `@昵称\n正文` 与 `ats`。
6. 发送失败沿用入站任务重试，不产生无 @ 的替代消息。

## 缓存与失败策略

个人微信群成员列表按群缓存 5 分钟，减少每次回复都请求 GeWe。缓存缺少发起人时强制刷新一次；仍找不到或接口失败则抛错。这样宁可重试，也不违反“回复必须 @ 对方”的铁律。

## 验收标准

- 群回复上下文明确标记必须 @，单聊不标记。
- 飞书、钉钉、企业微信都生成对应原生 @ 标记。
- GeWe `postText` 请求同时包含 `content=@昵称...` 和 `ats=wxid`。
- GeWe 找不到成员昵称时拒绝发送。
- 现有群回复、单聊、主动通知、重复发送防护测试全部通过。
