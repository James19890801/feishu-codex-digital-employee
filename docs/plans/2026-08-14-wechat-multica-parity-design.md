# 微信 Multica 同链路设计

## 目标

让个人微信复用飞书、钉钉现有的 Multica 任务闭环，包括查询、创建、确认、执行、进度同步、结果回复和文件产物回传。不得重放或补发历史消息，也不得为微信另建一套 Multica 业务逻辑。

## 方案选择

采用共享核心加微信适配层：Multica 的计划、确认、状态、订阅和产物校验继续使用现有组件；微信只补身份授权和文件传输。相比只发文本或跨渠道转发，这一方案能保持原会话闭环和三通道行为一致。

## 身份与权限

- Multica 查询、跟进和普通反馈继续允许当前微信会话使用。
- 创建、修改、评论、派发和执行仍只允许经过验证的 Owner self-chat。
- 微信的 Owner self-chat 定义为：GeWe 已鉴权回调中，由当前登录微信发往 `filehelper` 的单聊消息。
- 普通联系人私聊、微信群、伪造的 `selfChat` 元数据和 Owner 发往其他联系人的消息都不能获得写权限。
- 原有单次或双重确认规则保持不变。

## 数据流

1. GeWe 回调把发往文件传输助手的 Owner 消息标记为微信 self-chat。
2. 统一入站处理器继续使用现有 Multica 意图、计划和确认流程。
3. Issue 创建或执行时记录来源渠道、原会话、发送者和交付契约。
4. Multica 同步器按来源渠道把进度和状态只推回微信原会话。
5. 文字结果通过现有 GeWe `postText` 返回。
6. 文件产物下载到隔离目录并完成格式、大小和路径校验后，通过短时 HTTPS 文件租约暴露给 GeWe `postFile`，发送到原微信会话。

## 文件安全

- 文件 URL 使用 callback secret 作用域内的随机高熵 token，不暴露本机路径。
- 租约有短 TTL，过期后返回 404，并定期清理。
- 仅允许服务端显式登记且已校验的普通文件；不接受请求 URL 直接映射本地路径。
- 响应固定 `Content-Disposition: attachment`、`no-store` 和安全 MIME。
- GeWe 发送失败时保持 Multica 交付状态为失败，可由现有同步器重试，不伪报已交付。

## 兼容与错误处理

- 非微信通道行为不变。
- 微信通道不可用或公网回调不可用时，文本查询仍按原规则处理；文件交付明确失败并记录健康状态。
- 重启前检查 durable inbox，只有新消息进入新逻辑；历史完成、失败消息不重放。
- 用户可见文案按实际渠道显示“微信”，不再把微信误写成“飞书”。

## 验证

- 单元测试：微信文件传输助手识别、Owner 授权拒绝矩阵、GeWe `postFile` 请求、短时文件路由和过期行为。
- 集成测试：微信来源的 Issue 绑定、状态通知路由、文字结果和文件交付计划。
- 回归测试：飞书、钉钉 Multica 测试与全套机制验收保持通过。
- 上线检查：队列无待处理历史消息后重启，只对新消息生效。
