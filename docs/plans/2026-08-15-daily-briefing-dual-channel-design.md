# 每日早报钉钉与个人微信双通道投递设计

## 目标

复用现有每天 10:00 的“数字人测试群 AI 前沿早报”自动化。早报只生成一次，保留原钉钉群投递，并将同一内容的纯文本版本普通发送到个人微信群“AI流程与组织变革交流二群”。不创建第二条自动化，不在微信中 @ 所有人。

## 已确认目标

- 钉钉群：沿用现有自动化内已验证的群 ID。
- 个人微信群名：AI流程与组织变革交流二群。
- 个人微信群 ID：`53822548488@chatroom`。
- 运行时间：每天 10:00，Asia/Shanghai。
- 微信提醒方式：普通发送，不 @ 任何人。

## 方案比较

### 方案 A：在自动化提示词里直接调用 GeWe HTTP API

改动少，但 Token、请求格式、幂等和群身份校验散落在提示词里，容易误发或重复发送，不采用。

### 方案 B：新增第二条微信早报自动化

渠道隔离明显，但会重复检索和生成，两个版本可能不一致，也违背“不创建新自动化”的要求，不采用。

### 方案 C：现有自动化调用本地微信投递器（采用）

现有任务完成一次检索和写作，生成共享内容，再渲染为钉钉 Markdown 与微信纯文本。钉钉继续走 DWS；微信调用仓库内受测试保护的本地投递器。投递器从配置读取唯一目标群，从系统钥匙串读取 Token，发送前用 GeWe 核验群名，并以资讯日和群 ID 组成幂等执行键。

## 组件

1. `src/gewe-daily-briefing.mjs`
   - 校验资讯日、正文长度、群 ID 和群名。
   - 发送前查询 GeWe 群信息，防止群 ID 配错。
   - 使用 `executeMutationOnce` 防止同一资讯日重复发送。
   - 只发送普通文本，不设置 `ats`。

2. `scripts/send-gewe-daily-briefing.mjs`
   - 从 stdin 读取微信纯文本，避免长正文进入命令行参数。
   - 从 `config.local.json` 读取目标群和 GeWe 配置。
   - 从 macOS Keychain 读取 Token，不打印 Token。
   - 输出结构化 JSON 供自动化判断成功、重放或失败。

3. 现有 Codex 自动化 `ai`
   - 运行时间、模型、检索规则和钉钉发送保持不变。
   - 微信版移除 Markdown 标记和 `<@all>`，保留正文、来源 URL 与普通讨论邀请。
   - 钉钉和微信使用独立幂等机制；单边失败不补发另一边。

## 数据流

1. 自动化按原规则检索前一自然日资讯并生成一份事实底稿。
2. 从底稿渲染钉钉 Markdown 与微信纯文本，内容事实和排序一致。
3. 钉钉通过 DWS 使用原固定 UUID 发送。
4. 微信纯文本经 stdin 交给本地投递脚本。
5. 脚本核验配置、钥匙串、群身份和幂等状态后调用 GeWe `postText`。
6. 两个渠道分别记录结果；已成功渠道不因另一渠道失败而重发。

## 失败与重复控制

- 群 ID 与群名不一致：拒绝发送。
- Token 缺失或账号离线：拒绝发送并在自动化结果中报告，不发送半成品。
- 同一资讯日重复运行：钉钉复用原 UUID；微信返回 `replayed=true`，不再次调用 GeWe。
- 外部请求结果不确定：记录为 ambiguous，自动重跑被阻断，优先避免群内重复消息。
- 不发送测试消息，也不补发“发送成功”说明。

## 验收标准

- 自动化仍只有一条，时间仍为每天 10:00。
- 原钉钉投递指令保持有效。
- 个人微信目标固定为已确认的二群，且正文不含 `@所有人`、`<@all>` 或 `ats`。
- 同一资讯日第二次执行不会产生第二条微信消息。
- 群名不匹配时不会发送。
- 定向测试、完整测试、静态检查通过，并用自动化查看接口确认提示词已更新。
