# AI 原生的 Multica 空间选择设计

## 目标

用户在微信、钉钉、飞书等渠道创建 Issue 时，可以用自然语言选择实时候选空间。系统应理解“第六个”、“最后那个”、“培训那个空间”等表达，但不得编造空间 ID 或在不确定时猜测写入位置。

## 方案选择

1. 纯规则：继续扩充正则和模糊字符串。延迟最低，但无法稳定覆盖自然语言和会话指代。
2. 纯 AI：每次选择都调用模型。语义能力最强，但增加延迟和失败面，并会把原本确定的序号选择变成概率判断。
3. **混合式（采用）**：先用确定性解析器处理明确序号、完整名称和唯一模糊命中；只有未命中时，才调用受约束 AI 进行语义回退。

## 数据流

1. 用户处于 `multica_create_route` 的空间选择或 intake 阶段。
2. 确定性解析器先尝试匹配序号、空间 ID、名称、slug 和唯一近似名称。
3. 未命中时，运行时把以下最小信息发给 AI：
   - 当前用户回复；
   - 实时候选空间的 `id/name/slug/index`；
   - 本轮创建请求和有界的近期会话。
4. AI 只返回 JSON：`workspaceId`、`confidence`、`reason`。
5. 系统只接受“候选集中的精确 ID + high 置信度”。其他结果一律当作不确定。
6. 命中后继续原有的小队选择和创建确认链路；语义层不直接写入 Multica。

## 错误与交互

- AI 不可用、超时、返回非法 JSON、编造 ID、低置信度或多义时，不创建、不选默认空间。
- 首次询问可展示完整空间列表。用户回复后仍无法唯一判断时，只回复简短提示，不重复刷完整列表。
- 审计仅记录是否启用语义回退、结果类型、选中的候选 ID 和错误分类，不写入完整私聊历史。

## 测试与验收

- 确定性：`6`、`第6个吧`、`就选第六个呀`、完整空间名均不调用 AI 且正确命中。
- 语义命中：`最后那个`、`培训那个空间`、`放到刚才说的公开课那边` 可以在约束候选中命中。
- 不确定：多个候选都符合时继续追问，不写入、不选兜底。
- 防幻觉：AI 返回非候选 ID 必须被拒绝。
- 防刷屏：用户第二次表达仍不确定时，不再发全量空间列表。
- 回归：原有 Multica 创建、空间路由、小队选择、确认和 Owner 更新权限测试全部通过。
