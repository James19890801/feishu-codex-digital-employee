# 多渠道分组式每日学习设计

## 目标

把个人微信纳入现有每日分析与学习链路，与钉钉、飞书并列取数。每天最多读取 1000 条真实会话消息，并按渠道、群聊或单聊分别保留上下文，避免高流量会话挤掉其他群。

## 已确认范围

- 来源包括飞书、钉钉和个人微信 GeWe。
- 群聊和单聊都进入学习，但群聊按群独立组织。
- 未点名数字人、数字人没有回复的普通群消息也属于学习上下文。
- 总消息上限从 80 提升至 1000。
- “AI 流程与组织变革”等专业交流群获得更高取样权重，但不能独占全部额度。
- 学习用于改善行为和专业回答，不得在对外回复中暴露群名、人员、账号、项目、客户、合作关系、聊天原文或知识来源。

## 现状与问题

消息入口已经把飞书、钉钉和个人微信消息写入本地持久化存储，个人微信的普通群消息也会以静默上下文方式保存。现有 `learningEvidence` 将所有消息混成一个时间序列，学习提示词随后只取前 80 条，并且丢失 `chat_id`、`sender_id`、渠道和会话类型。因此：

1. 无法知道多条消息是否属于同一个群内讨论。
2. 高流量渠道可能挤掉其他渠道和群。
3. 每日学习无法稳定覆盖所有活跃微信群。
4. 无法按群名称识别需要重点学习的专业交流群。

## 方案选择

采用“本地全量留存 + 公平分组抽取 + 单次聚合学习”。

没有采用全局直接截取 1000 条，因为它仍会造成渠道和群聊饥饿。没有采用每个群单独调用一次模型，因为群数量增长后调用量、耗时和失败面都会线性增加。

## 数据流

1. 各渠道继续沿用现有入站链路，把真实消息写入 `conversation`。
2. 学习取数返回消息的 `chatId`、`senderId`、`channel`、`chatType`、时间和角色。
3. 系统按 `channel + chatId` 建立独立会话组，并在组内按时间排序。
4. 公平分配最多 1000 条消息：每个活跃会话先获得基础额度，剩余额度再按活跃度与专业群优先级分配。
5. GeWe 通过官方 `/gewe/v2/api/group/getChatroomInfo` 接口读取群名称；结果只缓存在本地。接口不可用时使用稳定匿名会话标识，学习不中断。
6. 专业群优先级只在本地计算。交给学习模型的是渠道、会话类型、匿名会话标识以及经过脱敏的消息序列。
7. 模型输出仍然只能是脱敏后的错误、任务方法、Skill 和长期行为规则。

## 公平抽取规则

- 每次学习最多 1000 条，不再使用 80 条上限。
- 每个活跃会话至少保留一段最新连续上下文；在活跃会话少于 1000 个时，任何会话都不能完全饿死。
- 同一会话中的消息保持原始时间顺序和发言人相对关系。
- 专业交流群使用权重加成，但仍受单会话上限约束。
- 优先保留最新消息、引用问答、任务交付、错误、图片或链接的已解析文本。
- 超过预算的旧消息仍保留在本地数据库，只是不进入当次模型上下文。

## 群名称与身份处理

GeWe 官方群信息接口返回 `chatroomId` 与 `nickName`。系统仅用群名称做本地分组显示和优先级判断，不把真实群名、微信 ID 或发言人 ID写入长期学习结果。

模型输入中的会话标识由本地稳定哈希生成，例如 `wechat-group-a1b2c3d4`。发言人也使用群内稳定匿名编号，使模型能理解多人上下文，但不能恢复真实身份。

## 隐私与安全

- 继续应用现有 `redactLearningText`，过滤手机号、邮箱、密钥、Token、文件路径和账号特征。
- 在学习提示词中明确禁止复述群聊原文或输出可识别实体。
- 长期记忆只保存抽象规则和方法，不保存真实对话、群名、成员名、项目名、公司名或客户信息。
- 群信息接口失败属于降级，不得阻断每日学习。
- 不为学习目的向任何聊天发送消息。

## 失败处理

- 单个群名称解析失败：记录脱敏审计，使用匿名会话标识继续。
- 个别消息字段异常：跳过该条，不丢弃整个会话组。
- 1000 条预算计算异常：回退到确定性的按会话轮询抽取。
- 模型分析失败：沿用现有学习任务失败和重试机制，不推进来源游标。

## 验证标准

1. 三个渠道都能出现在分组学习证据中。
2. 1000 条消息上限被严格执行，不再截断到 80 条。
3. 多个群同时活跃时，每个群都至少保留上下文。
4. 同一群消息顺序与发言人相对关系保持正确。
5. 专业群在预算紧张时获得更多上下文，但其他群不被清空。
6. GeWe 群名称接口失败时学习仍可完成。
7. 提示词和长期学习结果不包含真实群 ID、微信 ID、群名或其他敏感实体。
8. 上线后回补最近 24 小时的多渠道消息并触发一次手动学习，之后恢复每日增量学习。
