# 本地 Wiki 检索增强设计

## 目标

把这台 Mac 上可读取的知识资料，尤其是用户历史撰写的公众号 HTML，编译为一个本地、可追溯、持续更新的 Wiki，并在数字人通过微信、飞书、钉钉等通道回答专业问题时自动检索增强。

对外回答只呈现自然答案，不声明知识来源，不暴露原始文件名、路径、项目、公司、客户、合作方、联系人或其他敏感信息。

## 已确认边界

- GitHub 只用于研究公开检索方法，不是默认知识源。
- 本机原始文件只读，不移动、不改名、不覆盖。
- 系统目录、依赖、缓存、构建产物、密钥、Token、Keychain、浏览器数据、聊天原始数据库和隐藏凭据目录不入库。
- 公众号 HTML 是第一优先级知识源；其他文档后续可复用同一管线。
- 回答本身不能成为事实来源，避免错误自我强化。
- 没有足够证据时不使用本地知识；冲突材料不擅自裁决。

## 架构

采用 Karpathy LLM Wiki 的三层结构，并增加检索证据门和隐私门。

1. 原始资料层：保留文件原位，只记录内容哈希、修改时间和本地定位信息。
2. Wiki 编译层：生成按主题组织的脱敏 Markdown 页面，保留仅供系统内部使用的来源收据。
3. 检索层：关键词 BM25 与语义相似度混合召回，按问题重排候选片段。
4. 证据门：低于阈值、内容冲突或无法回溯原文时，不注入回答上下文。
5. 隐私门：在索引、Wiki 编译、检索输出和最终回答四处检测敏感实体；命中的专有项目、公司、客户和合作信息被删除或抽象化。

## 数据流

### 建库

1. 只读扫描用户目录中的 HTML 文件，排除系统目录、依赖、缓存、构建目录和临时文件。
2. 使用路径特征、标题、正文结构和公众号排版标记识别公众号 HTML。
3. 解析正文，去除脚本、样式、导航、一键复制控件和重复模板。
4. 将正文切成带标题层级的片段，计算稳定内容哈希。
5. 识别并剔除敏感实体；无法安全抽象的片段不进入可检索语料。
6. 生成本地 SQLite/JSON 索引和 Wiki Markdown 页面；内部来源收据与对外回答分离。
7. 增量扫描只处理新增或内容哈希变化的文件，删除文件对应条目标记失效。

### 回答

1. 在所有 IM 通道共用的回答入口判断是否需要检索。专业解释、方法、框架、经验总结和历史观点默认检索；寒暄、确认和纯操作命令不检索。
2. 对问题做关键词和语义查询，召回 Wiki 与安全原文片段。
3. 对候选进行相关性、来源完整性、时效性和敏感性重排。
4. 达到证据阈值时，将脱敏片段作为“内部参考材料”注入模型；提示模型不得声称、暗示或展示来源。
5. 未达到阈值时不注入，正常依赖模型通用知识回答；不得假称本地资料支持了结论。

## 隐私规则

- 不在模型上下文中传递绝对路径，只传递随机来源句柄。
- 不把文件名、目录名直接作为回答素材。
- 默认过滤组织名、人名、客户名、项目代号、账号、电话、邮箱、地址、合同金额和内部链接。
- 可泛化的案例改写为“某企业”“某项目”“某业务团队”；不可泛化的片段直接丢弃。
- 最终回答执行泄露扫描；若仍命中敏感实体，移除本地增强上下文并重新生成一次。
- 内部审计只记录来源句柄、哈希、得分和命中规则，不记录完整敏感原文。

## 失败处理

- 单文件解析失败：记录匿名错误并继续扫描。
- 索引不可用：回答链路降级为无本地增强，不发送错误话术给外部用户。
- 召回为空或低相关：不注入上下文。
- 多来源冲突：只提供不依赖冲突结论的内容，或在必要时表达“存在不同做法”，不披露具体来源。
- Wiki 页面生成失败：原始索引仍可检索，但不把失败产物当成证据。

## 验收标准

- 能识别并索引整机范围内的公众号 HTML，原文件零修改。
- 相同文件重复扫描不产生重复条目；修改后仅更新对应条目。
- 专业问题能召回相关公众号知识并增强回答。
- 普通闲聊不触发无意义检索。
- 低相关问题不会被无关本地材料污染。
- 测试样例中的公司、客户、项目、人名、路径和联系方式不进入模型提示或最终回答。
- 微信、飞书和其他通道复用同一套检索逻辑。
- 索引故障不影响现有消息收发。
