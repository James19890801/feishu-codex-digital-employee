# 明确 @ 数字人响应优先级设计

## 背景与根因

生产消息“……有能落地的规则再同步你。 @詹老师”已正常入站，但钉钉
`user_im_message_receive_group_all` 事件没有提供结构化 mentions。标准化层看到正文中存在
任意 `@某人`，将消息标成 `mentionedOther=true`。语义介入层又在识别数字人有效称呼之前
先处理 `mentionedOther`，最终以 `addressed_other` 静默完成。

这是触发归因错误，不是讨论价值、语义查重或主持机制的合理抑制。

## 目标

明确 @ 数字人时形成“响应义务”：正常介入选择机制不得把它压成无声；后续机制可以决定
回复是完整回答、简短确认、收束、拒绝越权或转交本人，但必须产生可见回应。

## 方案比较

### 方案一：只调整别名判断顺序

在语义介入层先识别数字人别名，再判断是否提到其他人。改动最小，但明确 @ 仍可能被后续
讨论冷却或语义重复机制静默抑制，无法满足“@ 必回应”。

### 方案二：贯穿式 `responseRequired`（采用）

识别结构化 @ 或正文中的已配置数字人称呼，形成显式响应义务。该标记贯穿介入、讨论预算
和语义重复门：介入与冷却不得静默；讨论或重复需要收束时发送简短确认。人工暂停、无效
身份、自身回声和限流等硬安全边界继续有效。

### 方案三：所有 @ 无条件绕过全部机制

最直接，但会绕过人工接管、防自循环、限流和风险控制，容易被刷屏或造成越权，不采用。

## 优先级

1. 硬安全边界：无效事件、应用或自身回声、本人明确暂停、滥用限流。
2. 明确目标识别：结构化 mention 或正文中直接 @ 已配置数字人称呼。
3. 响应义务：主持静默、语义介入置信度和普通冷却全部绕过。
4. 回复形态：正常回答、简短确认、收束、拒绝越权或转人工。
5. 执行边界：隐私、判断、承诺和外部写入仍按原风险规则处理。

“必须回应”不等于“必须执行”。高风险或越权请求必须回应边界说明，但不得执行。

## 数据流

正文和结构化 mentions 进入统一目标识别函数，产出：

```json
{
  "explicitAssistantMention": true,
  "mentionedOther": false,
  "responseRequired": true
}
```

同时 @ 数字人和其他人时，`explicitAssistantMention` 与 `mentionedOther` 可以同时为 true，
但响应义务优先，数字人仍回应。只有单独 @ 其他人时才继续旁听。

## 收束策略

当明确 @ 的消息遇到讨论收束或语义重复时，不再返回 silent suppress，而是发送稳定、简短的
确认，例如“收到，这条我看到了；有新问题我继续接。”该确认使用消息级幂等键，避免重试
造成重复发送。

## 验收

- 复现生产原句：无结构化 mentions、正文末尾 `@詹老师`，必须响应。
- 单独 @ 其他人：继续旁听。
- 同时 @ 数字人和其他人：必须响应。
- 明确 @ 遇到讨论冷却或重复：发送简短确认，不静默。
- 人工暂停、自身回声和无效身份：仍然抑制。
- 完整测试与机制验收无回归。
